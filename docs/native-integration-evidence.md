# Native integration evidence (2026-10-10)

These checks use source and synthetic fixtures. They do not read personal clipboard contents, issue attachments, user captures or account archives, and do not establish attended reproduction.

## Connection startup (#271)

`Worker::start_bot` supplies the official `UreqHttpClient::with_agent(proxy::agent())`. WhatsApp version discovery uses that HTTP client through `src/version.rs::fetch_latest_app_version` in whatsapp-rust revision `94c53e833805c58c9f5966b08d08c990650a651e`. It is separate from the Tokio WebSocket connector and its Happy Eyeballs behavior.

Pinned ureq 3.4.0 `src/unversioned/transport/tcp.rs::try_connect` tries resolved addresses sequentially. A configured connect timeout divides the available budget between them. Its default `Timeouts.connect` and `global` are both `None`; this previously let a blackholed first address wait on the OS before another address could be tried. Zap Fasterk now sets a 15-second connect budget using the supported [ureq configuration API](https://docs.rs/ureq/3.4.0/ureq/config/struct.ConfigBuilder.html#method.timeout_connect). A synthetic configuration fixture checks the budget, dual-stack `IpFamily::Any`, retained certificate verification and unchanged WebPKI roots. This covers timeout-based fallback; ureq still aborts on other errors such as network-unreachable instead of continuing through the remaining addresses. Complete fallback for those errors belongs in ureq or a supported connector, and must not be claimed as fixed here. DNS, TLS negotiation and response/body stalls are separate from the TCP connect budget.

TLS interception is another path. Current ureq rustls defaults use `RootCerts::WebPki`, not the OS enterprise certificate store. The supported `RootCerts::PlatformVerifier` option exists, but rustls requires ureq's `platform-verifier` feature, currently absent. That is an available implementation choice, not a missing protocol API. A certificate error must be reproduced with sanitized failure class, affected stage, installed enterprise trust and revocation connectivity before choosing a trust policy. Do not disable verification, force IPv4 for all networks, delete the session or relink as a shortcut. No trust-policy change was made during this audit.

## Windows video clipboard (#323)

Zap Fasterk reads `arboard::Clipboard::get().file_list()` before images and routes existing video paths through ordinary attachment staging. Pinned arboard 3.6.1 `src/platform/windows.rs::Get::file_list` calls `clipboard_win::raw::get_file_list_path`, which reads `CF_HDROP`. Image reads support image formats, not video byte streams. Existing synthetic clipboard tests cover file-list priority and image fallback.

Microsoft documents a different virtual-file contract: `CFSTR_FILEDESCRIPTOR` plus indexed `CFSTR_FILECONTENTS`, accessed through `IDataObject::GetData` and `FORMATETC.lindex`. Content can arrive through `IStream`, storage or global memory. See [Shell clipboard formats](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard#cfstr_filecontents). Arboard's public file/image readers do not expose that contract. The source available here does not establish which format a particular Snipping Tool version supplies, so virtual-file support cannot be asserted as the reproduced missing path. Needed evidence is an attended synthetic recording with format names/IDs and storage-medium type only, without clipboard bytes or filenames from personal captures. Once identified, a bounded Windows adapter can stage a private temporary attachment on explicit paste, validate size/type, and clean up on cancellation and account change. An upstream arboard API would also be suitable; neither route requires a protocol fork. Saving a recording then copying its file already uses the supported path.

## GNOME outer border (#397)

Zap Fasterk leaves native decorations enabled. `ViewportBuilder::with_titlebar_shown(false)` is documented as macOS-only, so it does not suppress Linux decorations. Pinned egui-winit revision `ba6790fe7cf46e58e8d27ce1524cbfdee745e938` passes `decorations.unwrap_or(true)` to winit. Pinned winit revision `ed7caa9023f10b397f5b6ec8284a840cbd8a6f65`, Wayland `window/state.rs`, creates an Adwaita/fallback frame when the negotiated decoration mode is client-side; server-side mode drops that frame. Thus frame ownership depends on compositor negotiation and window backend, rather than egui widget corner radii.

A supported app option can disable decorations, but would also remove native frame controls and edge-resize handling. This is not a safe cosmetic fix without replacement interaction and attended verification. The existing public viewport/window API does not expose a native frame corner-radius override. Needed evidence is a synthetic app window on the reported GNOME session, Wayland versus X11/XWayland, negotiated decoration ownership, and whether the rectangle belongs to native framing, compositor shadow or app content. A confirmed native-frame defect should be fixed in the shared winit/eframe/decoration stack, preserving resizing, shadow and readable contrast. No dependency patch or speculative decoration toggle was added.


## Arabic, Hebrew and bidirectional text (#328, #398, #248)

Current source already has script-aware shaping and bidirectional layout. Pinned epaint revision `ba6790f` in `crates/epaint/src/text/text_layout.rs` computes Unicode embedding levels, splits font runs at direction changes and passes each run's direction to harfrust. `src/bidi.rs` subsequently places shaped runs in visual order after wrapping while retaining logical glyph indices for copy, links and carets. Its fixtures cover Hebrew niqqud, embedded URLs, narrow ellipsis and Arabic lam ligatures. `src/markup.rs`, composer fields and group-name fields use this layout. These are implemented capabilities; a report from an older build does not establish a current absent bidi API.

Pinned fastframe-fonts revision `23d87e0`, `crates/fastframe-fonts/src/system.rs`, probes installed Arabic and Hebrew fallback faces, aligns their baselines and enlarges small Arabic faces. Epaint `font.rs::styled_metrics` computes each face's ascent, descent and leading; `resolve_face` chooses a glyph-capable fallback. The remaining clipping or Hebrew appearance reports require a synthetic reproduction using the actual selected font family, platform, scale and glyph ink bounds against the field clip rectangle. No user's messages or font screenshots were read. Current source alone does not prove every Arabic diacritic or Hebrew face fits on every platform, and it does not prove parity with Android's paragraph alignment. A confirmed rasterization/face-metrics defect belongs in the shared font/epaint implementation; application padding should change only when the fixture demonstrates an app-owned clip boundary. No crate patch or blanket font replacement was added.
